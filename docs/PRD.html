vigilant‑engine — AppSec Findings Pipeline & Dashboard

Normalizing SAST, SCA, secret, and (planned) DAST/container scanner output into one schema, deduplicated and queryable, with a dashboard reading real scan data — a portfolio demonstration of AppSec engineering judgment.

01

Problem

Security scanners (SAST, SCA, DAST, secret, container) each produce findings in their own JSON shape, with no shared severity scale and no cross-tool identity for “the same issue.” Nothing persists once a CI job ends. A team running several scanners has no single place to answer what’s actually open right now, across every tool, at what severity — that requires normalizing and storing what today lives only in disconnected job logs.

02

Goal & non-goals

Run real scanners against a real vulnerable app, normalize every tool’s output into one schema, deduplicate repeat findings across runs, and surface the result on a dashboard — as a portfolio-grade demonstration of tool selection, schema design, CI integration, and secure-by-default choices. Not a production vulnerability-management platform.

  • Not built to scan arbitrary user-supplied repos — one fixed demo target.
  • No ticketing, SLA tracking, or remediation workflow.
  • Not optimized for scanner throughput — correctness and clarity over scale.

04

Known gap: run history

Deferred · scoped to Phase 5

Finding carries per-row first_seen / last_seen, which answers “is this still open” but not “how did the count change from run to run.” Closing that needs a scan_runs table — one row per run, with a timestamp, commit, and per-severity snapshot — a schema addition, not a rewrite. It’s gated on Phase 5’s volume-backed database also landing, since there’s no point tracking run history a container restart would wipe. Until then, the dashboard’s open-vs-fixed trend stays deliberately unbuilt rather than built against faked data.

Process note — how this gap was caught

Worth recording as process, not just outcome: this requirement was initially cited, not tracked.

Phase 4 checklist, as written “It needs history across multiple scans, which needs the scan_runs table gap already flagged in Phase 3.” Read at face value: “don’t worry, this is already covered elsewhere.” It wasn’t — Phase 3 only flags persistence (the DB surviving past one CI job, closed by Phase 5’s volume and Phase 7’s RDS). Neither phase ever asked for a scan_runs table. Persistence and run history are different problems — a volume-backed findings table still only gives per-finding first_seen/last_seen, never a queryable list of runs.

The citation pointed at a requirement that existed nowhere as a tracked task — an assumption stated once, inside the very bullet deferring work because of it. Left unchecked, it would likely have stayed unbuilt indefinitely. It’s now its own explicit item under Phase 5 (§4.5).

05

Out of scope for now

  • IaC scanning (Checkov / tfsec) — no Terraform or Kubernetes manifests exist yet; revisit if Phase 7 (AWS deployment) happens.
  • Multi-repo or multi-target scanning — one fixed demo target by design.
  • Auth / RBAC on the dashboard — single-user portfolio project, not a multi-tenant product.

Success criteria

✓Met — a single CI run produces normalized, deduplicated findings queryable by severity and source within seconds of the run finishing.
✓Met — the dashboard shows the same numbers the CI run’s /stats smoke test printed, with no manual data entry.
✓Met — every non-trivial design decision (target app choice, scanner set, dedupe strategy, defer-vs-build calls) is traceable to a written reason, tracked in the phased build plan.
