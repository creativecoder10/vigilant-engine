Bill of materials

Item Component Spec
01 demo-target/ OWASP Juice Shop, run via its official Docker image — a well-known, intentionally-vulnerable app (SQLi, XSS, broken auth, vulnerable deps) with an active challenge tracker.
02 .github/workflows/ Runs Semgrep, npm audit, Snyk, and gitleaks against the source; runs Juice Shop in a container and points ZAP's baseline scan at it; runs Trivy against the built ingestion/dashboard images. Posts every tool's raw output to the ingestion API.
03 ingestion/ FastAPI + SQLModel service. Per-scanner parsers map raw output onto the shared Finding schema, dedupe by hash, and upsert into SQLite.
04 dashboard/ Next.js app reading the ingestion API's /findings and /stats endpoints — severity breakdown, open vs. fixed, trend over time, by tool/category.

Not a per-juice-shop-commit trigger. demo-target/ is a git submodule — a pinned pointer to one upstream juice-shop commit, not a live copy. Juice Shop's own repo can advance indefinitely without this workflow ever noticing. It only re-runs when vigilant-engine's own repo changes — including the commit that deliberately bumps the submodule pointer.
The database is thrown away every single run. Step 4 starts the ingestion API fresh, backed by an empty SQLite file that exists only for that job. Nothing persists once the job ends — every run starts from zero findings, so there's no trend data yet. That's a deliberate, named simplification: this phase proves the scan → normalize → store → query loop works; pointing it at a permanently hosted API so findings actually accumulate is later (packaging/deployment) work.

Step-by-step detail

Step What happens Worth knowing
01 Trigger GitHub Actions fires on push to main or any pull_request, both on vigilant-engine's own repo.
02 Checkout actions/checkout with submodules: true — without it, only the submodule's commit pointer comes down, not its files.
03 Env setup Python 3.11 for the ingestion service and scanner scripts; Node 22 because Juice Shop is a Node app and npm-based scanners need it.
04 Ingestion API up uvicorn started as a background process, polled on /docs until ready, backed by a fresh empty SQLite file for this run only.
05 Target deps npm install inside demo-target/ so scanners have real code and a resolved dependency tree to check.
06 Run scanners Each tool writes its own raw JSON file. Steps end in || true since a scanner exiting non-zero usually means "found something," not "crashed" — the goal here is ingestion, not gating the build.
07 Post results post_to_ingestion.py POSTs each raw JSON file to /ingest — one shared script, one call per tool.
08 Normalize The API's /ingest handler runs a per-tool parser that maps that tool's own JSON shape into one common Finding schema — see Page 3.
09 Store + smoke test Normalized rows are upserted into SQLite by dedupe_hash. The job's last step prints GET /stats, proving the loop worked — it is not the dashboard.

Aside — FastAPI/uvicorn vs. Express/Node

Layer Node.js + Express Python + FastAPI
Routes & logic Express — app.get('/findings', handler). Defines what happens per request. FastAPI — @app.get("/findings"). Same job, same shape.
Socket + HTTP parsing Node's own http module (built into the runtime, on top of libuv). Express is a thin layer over it, not a replacement for it. uvicorn — a separate ASGI server process. The Python interpreter has no built-in production HTTP server; ASGI exists so any compliant server (uvicorn, Hypercorn, Daphne) can drive any compliant app (FastAPI, Starlette).
How you start it One process, one command: node server.js. Express's app.listen(3000) is just a convenience wrapper around Node's own http.createServer(app).listen(3000) — the listening call lives inside your own file. Two separate things: your file builds the app object (line 34 of app/main.py), but nothing in that file opens a socket. A separate command drives it: uvicorn app.main:app --port 8000.
The one-line reason. Node was built from the ground up as a runtime for non-blocking network I/O — an HTTP-capable socket server ships inside the language runtime itself, so app.listen() "just works" from inside your script. Python's interpreter carries no such thing; that gap is exactly why the ASGI spec — and a separate program to implement it, uvicorn — had to exist as its own piece.

Example A — Semgrep (SAST)

RAW · one entry in semgrep --json's "results"
{
  "check_id": "python.lang.security.
               audit.eval",
  "path": "routes/login.py",
  "start": { "line": 42 },
  "extra": {
    "message": "Detected eval() with
                 user input",
    "severity": "ERROR"
  }
}
→
NORMALIZED · Finding row
source      = semgrep
rule_id     = python.lang.security.
              audit.eval
title       = "Detected eval() with
               user input"
severity    = HIGH     # ERROR → HIGH
file_path   = routes/login.py
line_number = 42
dedupe key  = rule_id + file_path
              + line_number

Example C — npm audit (SCA)

RAW · vulnerabilities["lodash"]
"lodash": {
  "severity": "high",
  "range": "<4.17.21",
  "fixAvailable": true,
  "via": [{
    "source": 1523,
    "title": "Prototype Pollution",
    "url": "https://github.com/
            advisories/..."
  }]
}
→
NORMALIZED · Finding row
source          = npm_audit
rule_id         = 1523
title           = "Prototype Pollution"
severity        = HIGH
package_name    = lodash
package_version = <4.17.21
file_path       = null   # SCA is
                  package-level, not
                  line-level
dedupe key      = rule_id
                  + package_name
The dedupe_hash formula, exactly. compute_dedupe_hash(*parts) joins whatever identifying parts a parser passes it with "|" and SHA-256s the result. It never includes a timestamp or scan-run ID — only fields that identify what the finding is. So the same real issue found on run 1 and run 50 hashes identically, and POST /ingest upserts the existing row (bumping last_seen) instead of inserting a duplicate. Note the SCA case: npm audit hashes on rule_id + package_name only, with no file/line, because two different packages can share one advisory and a single package has no line number to point to.
Reopening a "fixed" finding. If a finding's dedupe_hash already exists in the table with status = FIXED, and a later scan reports that exact same hash again, the upsert flips it back to OPEN before bumping last_seen — the reasoning being that whatever fix closed it clearly regressed if the scanner is seeing it again.

Field mapping cheat sheet

Concept Semgrep (SAST) gitleaks (secrets) npm audit (SCA)
Location path + start.line File + StartLine none — findings are package-level, not line-level
Severity source extra.severity (ERROR/WARNING/INFO), mapped to HIGH/MEDIUM/LOW none — every hit is hardcoded CRITICAL vulnerabilities.<pkg>.severity (critical/high/moderate/low/info); "moderate" renamed to MEDIUM
Dedupe identity rule_id + file_path + line_number rule_id + file_path + line_number rule_id + package_name (no file/line)
Extra fields kept none beyond the common set commit_sha; fixed remediation sentence ("rotate the credential") package_name, package_version; remediation ("npm audit fix" or manual)
