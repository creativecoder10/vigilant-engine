  2. Trust boundaries concept learned

    What it is: a line drawn across the DFD, cutting through specific data-flow arrows, marking a point where the level of trust or control changes between what's on either side. Not every arrow crosses one — only the ones where you'd genuinely have to verify something (identity, permission) before letting data through, if you were being careful.

    Common kinds, so you can recognize one when you see it:

    • Network boundary — internet vs. your internal network
    • Process/machine boundary — data leaving one process/container and entering another you don't fully control
    • Privilege boundary — anonymous user vs. authenticated user, regular user vs. admin
    • Physical boundary — on-prem vs. cloud, your infra vs. a third party's

    How to find them, mechanically: go arrow by arrow and ask one question — "do both ends of this arrow trust each other equally, or does crossing it mean going from something I don't control to something I do (or from lower privilege to higher)?" If yes to the second, draw a boundary line across that arrow. If both ends are things you fully control at the same privilege level, no boundary — it's just internal plumbing.

    Why STRIDE cares: threats cluster at boundaries, not in the interior. An attacker has to cross a boundary to do damage — the one point where they're forced to either hold valid credentials or exploit something that lets them skip needing them. Everything sitting entirely on one side of every boundary has a much smaller realistic threat surface than anything a boundary-crossing arrow touches.

    Applied to the practice sketch: CI → POST /ingest (boundary — CI is outside your control), Process ↔ DB INSERT/UPDATE/SELECT (no boundary — your own API talking to its own DB, same trust level), Process → GET /findings, /stats → Dashboard (boundary — a separate, externally-driven client). One boundary line covers both crossings, since they're the same boundary conceptually: "anything outside vigilant-engine's own process."

    Why each cell is what it is (worth understanding, not memorizing):

    • Spoofing only applies to things that have or claim an identity — a user, a service, a process. A data flow or a data store isn't "someone," so it can't be impersonated. That's why only External entity and Process get an S.
    • Repudiation only applies to things that take an action that could later be denied — a user denying they did something, a process denying it handled a request. A data store gets it only when it's specifically a log — a log's entire job is being the evidence that defeats repudiation; if that log can be silently altered or deleted, repudiation becomes possible again. findings.db isn't a log in that sense (it's primary data, not an audit trail), so no R for it.
    • Tampering and Information Disclosure apply to anything that holds or carries data — flows (data in transit can be intercepted/modified) and stores (data at rest can be read/altered). Doesn't apply to an external entity itself — you don't "tamper with a user," you tamper with what they send, which is a flow.
    • Denial of Service applies to anything that must stay available — flows can be flooded, stores can be exhausted/locked, processes can be crashed. External entities are outside your system, so keeping them "available" isn't your problem.
    • Elevation of Privilege only applies to a Process — it's the only element type that actually executes with a privilege level. A data store or a flow has no privilege to escalate into.

    Applied to the practice sketch, row by row:

    • CI scanner jobs (external entity) → Spoofing, Repudiation
    • Dashboard (external entity) → Spoofing, Repudiation
    • Ingestion API (process) → all six
    • findings.db (data store, not a log) → Tampering, Information Disclosure, DoS
    • Each data flow (POST /ingest, INSERT/UPDATE, SELECT, GET) → Tampering, Information Disclosure, DoS
    What falls out for free: the Process is the only element carrying all six threat categories, and it's also the only element sitting on both sides of the trust boundary — exactly why it's the highest-value thing to scrutinize. The table isn't just bookkeeping; it tells you where to spend your attention.

All three items are concept-level — the systematic walk itself (applying this table row-by-row to real elements) is the work of Phase 2, not yet done.

The approach taken for Phase 2 — how to actually assess the data flow

Not pure static code reading — the standard AppSec method blends black-box traffic observation and white-box source reading, with a debugger as an occasional deep-dive tool, not the default. In priority order, per flow:

  1. Watch the real traffic first (black-box). Before touching source, perform the action live in the running app and watch what actually crosses the wire — code can have dead paths or behavior that differs from what a quick read suggests, so this is the most reliable way to know the real data flow.
    • Browser DevTools → Network tab — zero install, works immediately against the running Juice Shop instance. Inspect the exact URL, method, request body, response body, and any headers/cookies set.
    • An intercepting proxy — Burp Suite (Community, free) or OWASP ZAP (already in the scanner list) sit between browser and server and let you see, and even modify, every request live. Worth learning regardless of this project — one of the most standard AppSec tools there is. Installed via brew install --cask burp-suite (Community Edition, free) — no VM/Kali needed, it's a regular desktop app. Setup: launch → Temporary project → Use Burp defaults → Proxy tab → Intercept → Open Browser (Burp's own pre-configured Chromium, certificate already trusted) → browse the app in that window; every request lands in Proxy → HTTP History. Core workflow: right-click a request → Send to Repeater to edit and resend it repeatedly (replaces retyping curl commands); Comparer to diff two responses side by side; Target → Site map to see every endpoint touched this session.

    This step answers the data flow arrows precisely: what's actually in the request (just email + password, or more?), what's in the response (a JWT? where — body or cookie? does it leak more fields than needed?).

  2. Read the source second (white-box), now that the endpoint is known. Traffic capture can't show server-side logic — only inputs and outputs. Grep for the exact route (e.g. POST /rest/user/login) in demo-target/routes/, follow it into the handler, read it step by step: DB query, password comparison, token issuance. This fills in the Process internals.
  3. For the DB layer, don't guess from model code — turn on query logging. Juice Shop uses Sequelize, which has a config option to print every SQL statement it runs to the console. Flip it on, trigger the action again, and see the literal SELECT/INSERT executed — more reliable than reading model definitions and inferring the query.
  4. A debugger is the last resort, not the first move. Attaching Node's inspector (node --inspect) with a breakpoint in the handler is useful when the first three steps leave something ambiguous (e.g. which of two code paths actually executes) — but too slow to use as the default method across a whole flow.
Why this order, not source-reading alone: black-box traffic tells you ground truth about what's transmitted; white-box reading tells you what happens inside the box; query logging confirms the data store interaction directly; the debugger is for resolving ambiguity, not for first-pass mapping. Using only source reading risks modeling code paths that aren't actually reachable, or missing behavior that only shows up at runtime.

What actually happened: black-box (DevTools/Burp) and white-box (source review) exploratory testing, guided by the OWASP API Security Top 10 rather than a formal DFD-first walk, produced 10 confirmed findings, 0 open candidates (JWT over-exposure; two flavors of basket BOLA — a missing check and a bypassed one; mass user-table disclosure; unauthorized product-price tampering; no login rate limiting; non-expiring JWTs; CORS/CSP gaps; exposed API schema; a whoami field-allowlist gap). 3 OWASP categories (API4, API6, API7) deliberately time-boxed, not tested — reasoning documented per-category in THREAT_MODEL.md. Roadblocks and conceptual corrections made along the way (kept here so this checkpoint is reviewable, not just a status line):
  • Confusing a "bounded flow" (an analyst's scoping choice — pick a tractable slice of the app) with a "trust boundary" (a property of the system — where trust level actually changes) because they share a word.
  • Assuming trust boundaries only separate privilege levels (customer vs. admin) until the basket BOLA showed they also separate identities at the same level (your data vs. a peer's).
  • Briefly misattributing the basket-tampering bug to the clarinet parsing library, when the library behaved correctly and the bug was Juice Shop's own inconsistent use of its output.
  • A real, diagnosed-from-first-principles tooling bug: Juice Shop's own shipped demo-target/threat-model.json (authored by the maintainer in 2021) opened in the current Threat Dragon app (v2.6.2) with a completely blank canvas — no error, despite the file clearly containing 31 cells. Diagnosed by pulling real example files from Threat Dragon's own GitHub repo and diffing the JSON structure field by field: the old file uses a pre-rewrite v1.x schema (diagramJson.cells nested, no version field, type: "tm.Process", flow endpoints referencing element IDs directly) while the current app expects a newer schema (cells flat, version present, shape: "process", flow endpoints referencing {cell, port} pairs). A breaking format migration that fails silently rather than erroring — a genuinely common class of bug with any tool that's changed its file format.
  • An engineering decision made, then reversed, honestly: the first plan was to rebuild the diagram by hand in Threat Dragon's GUI, reasoning that a script-generated file risked being silently broken the same way (new-format flows need per-element port IDs normally only generated correctly by the GUI). After a long, slow manual click-through, this was revised: the actual fix was to generate the file with a script and validate it structurally (every flow's source/target cell+port reference checked programmatically to resolve to a real port on a real node) before treating it as done — a stronger correctness guarantee than a manually-clicked diagram, and far faster. The schema itself was confirmed from two sources: OWASP's own GitHub repo demo files, cross-checked against a file the installed app itself produced when saving a new blank model. Worth being candid that the first decision was the more cautious-sounding option, not the actually-better one — reversing it rather than sunk-costing through the slower path is itself worth describing honestly in an interview.
What a "threat model" actually is, and threats-by-element-type as a generative exercise: a threat model is a DFD plus the STRIDE threats found against it — necessarily specific to one system's real architecture, not a reusable template (Threat Dragon ships several unrelated demo models — Cryptocurrency Wallet, IoT Device, CMS — purely as worked examples, not starting points for Juice Shop). Threats attach to any DFD element type (actor, process, store, or flow), not only arrows; all 10 confirmed findings here happen to sit on one flow (Angular Frontend → Application Server) because that's the one edge every finding was actually discovered on — an honest reflection of testing scope, not a limitation of the tool. Being able to name untested threats the same diagram invites at other element types (e.g. "is MarsDB NoSQL DB exposed to open network access," "does B2B API enforce the same checks as the customer path") using only the per-element-type STRIDE table — see STRIDE_METHODOLOGY.md's "Threats by DFD element type" section — is a stronger interview signal than the diagram alone: it demonstrates the reasoning is generative, not pattern-matching against Juice Shop's own pre-seeded, named challenges (visible directly in source as changeProductChallenge, passwordHashLeakChallenge, etc.). Every real pentest/assessment report carries a "scope and limitations" section for exactly this reason — a finished report is never claimed as exhaustive coverage.
